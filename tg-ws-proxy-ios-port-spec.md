# Спецификация: перенос механизма tg-ws-proxy на iOS (для SwiftGram)

Дата составления: 23 сентября 2026. Документ собран по итогам исследования исходников Flowseal/tg-ws-proxy, официальной документации Apple NetworkExtension и актуальной (сентябрь 2026) картины блокировок Telegram/VPN в РФ. Предназначен как техническое задание для дальнейшей реализации (в т.ч. AI-агентом).

## 1. Цель

Перенести логику обхода блокировки Telegram (проект Flowseal/tg-ws-proxy, Python, десктоп) в iOS-окружение так, чтобы SwiftGram (форк Telegram-iOS) получал ускоренное/разблокированное соединение с датацентрами Telegram без ручной настройки прокси в самом приложении.

## 2. Как работает оригинальный tg-ws-proxy (референс)

### 2.1 Структура исходника
- `tg_ws_proxy.py` — точка входа, `asyncio.start_server`, разбор клиентского init-пакета.
- `bridge.py` — `CryptoCtx` (4 независимых AES-256-CTR контекста) и `MsgSplitter` (сборка/разбор границ MTProto-сообщений).
- `pool.py` — пул прогретых WS-соединений.
- `balancer.py` — ротация Cloudflare-доменов, cooldown/blacklist логика.
- `raw_websocket.py` — минимальный WS-клиент.
- `fake_tls.py` — маскировка под TLS 1.3 (`ee`-secret режим), включая обработку active probing через проксирование на реальный masking-домен.
- `config.py` / `utils.py` — константы протокола (`SKIP_LEN`, `PREKEY_LEN`, `IV_LEN`, таблица DC).

### 2.2 Протокольная логика (переносима практически 1:1)
1. Клиент шлёт 64-байтный obfuscated init-пакет.
2. Из него извлекаются `prekey`+`iv`, ключ = `SHA256(prekey + secret)`, AES-256-CTR расшифровка.
3. Внутри: 4-байтный `proto_tag` + 2-байтный signed little-endian `dc_idx` → `abs(dc_idx)` = DC ID, знак = `is_media`, значения ≥10000 = тестовые DC (реальный ID = `dc − 10000`).
4. Генерируется новый `relay_init` (свой случайный 64-байтный init с тем же `proto_tag`) для соединения с реальным датацентром/релеем.
5. Трафик клиента **не форвардится байт-в-байт**, а полностью переупаковывается: расшифровка по ключу клиента → зашифровка по новому ключу для DC (и обратно) — 4 независимых крипто-контекста.

### 2.3 Каскад фолбэков соединения (в порядке приоритета)
1. Пул готовых WS-соединений (`ws_pool`).
2. Прямой WSS к `kws{dc}.web.telegram.org` (официальный домен Telegram Web).
3. Cloudflare Worker (`--cfproxy-worker-domain`, ставится самостоятельно).
4. Ротируемые CF-домены (`.github/cfproxy-domains.txt`, автообновление с GitHub), с cooldown при HTTP 429 (45с → рост до 5 мин).
5. Прямой TCP к IP датацентра — последний фолбэк.

Черные списки с TTL: `IP_FAIL_COOLDOWN=3600с`, `DC_FAIL_COOLDOWN=60с`.

### 2.4 Лицензия
MIT. Совместима с инкорпорированием в GPL-проект (Telegram-iOS/SwiftGram) при сохранении атрибуции.

## 3. Почему это работает (и когда перестаёт)

### 3.1 Экономика блокировки
Cloudflare/AWS IP обслуживают миллионы не связанных с Telegram сайтов — блокировать эти диапазоны целиком дороже для цензора, чем не блокировать. WS-обёртка делает трафик похожим на обычный WSS-сеанс к легитимной CDN-инфраструктуре.

### 3.2 Ограничения метода (актуально на сентябрь 2026)
- **`web.telegram.org` заблокирован на уровне маршрутизации (L4 blackholing)** — TCP-соединение отваливается по таймауту, а не по DPI-анализу. Первый уровень фолбэка (прямой WSS к домену Telegram) может быть неработоспособен независимо от маскировки.
- **`t.me` полностью удалён из DNS-зоны с 14 июля 2026.**
- Независимый тест te-st.org (август 2026) показал: Telegram остался заблокирован при всех протестированных инструментах обхода, включая tg-ws-proxy (тестировали десктопную версию).
- **Голый FakeTLS без реального relay-backend ловится быстро** — подтверждено эмпирически пользователем. Причины: (а) active probing — ТСПУ сам стучится на "домен" маскировки, и если backend не отвечает как настоящий сайт — мгновенный флаг; (б) фиксированная TLS-сигнатура (JA3/JA4) у типовых FakeTLS-реализаций; (в) репутация подсети; (г) поведенческие паттерны (залповые коннекты).
- Значит **обязательное условие жизнеспособности** — реальный domain fronting / TCP-сплайсинг на действительно работающий backend (как это делает Cloudflare-фолбэк), а не локальная имитация байтов.
- **Режим "белых списков" (drop-all по IP)** — отдельный, более грубый механизм, включается ситуативно (синхронизирован с угрозами атак БПЛА, крупными событиями), создаёт огромную нагрузку на ТСПУ-оборудование и коллапс инфраструктуры (банки, платёжные терминалы). В этом режиме никакая маскировка протокола не поможет — блокировка идёт по IP на L3 до DPI-анализа. Cloudflare и зарубежные CDN не входят в белый список.
- Обычный день-к-дню режим — сигнатурный ТСПУ/DPI (JA3/JA4-фингерпринтинг, анализ размеров пакетов) — именно против него эффективен WS+CF-подход.
- Известный кейс: MTProto из **родного** мобильного клиента (без обёртки) заблокирован на конкретной сотовой сети, при этом тот же физический канал (та же SIM, раздача на ПК) пропускал WS-обёрнутый трафик через tg-ws-proxy — подтверждает, что блокировка триггерится по фингерпринту клиента/протокола, а не по типу устройства/сети.

## 4. Архитектура на iOS

### 4.1 Ключевое отличие от Telegram Desktop
На десктопе пользователь вручную указывает прокси в настройках Telegram. На iOS **в самом SwiftGram ничего не настраивается** — перехват происходит на уровне ОС.

### 4.2 Механизм перехвата — NEPacketTunnelProvider
- Используется `NEPacketTunnelNetworkSettings` с `includedRoutes`, ограниченными IP-диапазонами датацентров Telegram (а не глобальный VPN).
- Apple прямо запрещает использовать Packet Tunnel Provider как "листенер"/прокси-сервер (TN3120) — весь функционал должен жить внутри цикла обработки IP-пакетов (`packetFlow.readPackets`/`writePackets`), а не как отдельный сервис, к которому подключаются извне.
- **Критическая техническая сложность**: `packetFlow` отдаёт сырые IP/TCP-пакеты, а не уже принятые сокеты (в отличие от `asyncio.start_server` в оригинале). Нужен собственный userspace TCP/IP-стек внутри расширения, чтобы "принять" TCP-хендшейк от SwiftGram и получить байтовый поток — это стандартная практика (tun2socks + lwIP, C-библиотека, BSD-лицензия), используется во всех похожих проектах (Shadowrocket, Mullvad, iCepa/Tor для iOS).
- Исходящее WS-соединение (`URLSessionWebSocketTask`) создаётся самим extension-процессом и не перехватывается собственным туннелем (иначе рекурсия).

### 4.3 Поток данных (итоговая схема)
```
SwiftGram → TCP к IP датацентра (как обычно, ни о чём не знает)
   → iOS матчит по includedRoutes → перенаправляет на TUN-интерфейс
   → packetFlow.readPackets → сырые IP-пакеты
   → lwIP/tun2socks → восстановленный TCP-байт-поток (аналог accept())
   → Swift-порт логики tg_ws_proxy.py: парсинг init → DC ID → relay_init → AES-CTR реэнкрипция
   → WS/WSS наружу (URLSessionWebSocketTask), каскад: пул → прямой WSS → CF Worker → CF-домены → TCP
   → ответ → расшифровка → упаковка в TCP → lwIP формирует IP-пакеты → packetFlow.writePackets
```

### 4.4 Гибкость определения трафика — два подхода
1. **По destination IP (`includedRoutes`)** — client-agnostic: работает автоматически для любого MTProto-клиента на устройстве (SwiftGram, официальный Telegram, форки), без поддержки списков bundle ID. Рекомендуемый базовый уровень.
2. **По приложению (Per-App VPN)** — официально требует MDM-управления приложением. Но есть легальный developer-only способ без MDM: `NETestAppMapping` в `Info.plist` + конфигурационный профиль с payload `com.apple.vpn.managed.applayer` (`VPNUUID`) — задокументированный Apple механизм для тестирования, работающий на обычном устройстве без сервера MDM. Даёт точный контроль по списку bundle ID.

### 4.5 Ограничение по Mini Apps
Telegram Mini Apps работают через отдельный канал — WebView с "unrestricted outbound networking" к произвольным сторонним доменам backend'а мини-приложения, параллельно основному MTProto-каналу. IP-based туннель (п. 4.4.1) их не перехватывает и не ускоряет. Per-app VPN (п. 4.4.2) захватит их трафик, но внутри провайдера нужна отдельная ветка: детект "это MTProto-хендшейк vs обычный HTTPS" и bypass-режим (прозрачный форвард без обработки) для не-MTProto-трафика.

## 5. Маппинг модулей Python → Swift/C

| Python | Функция | iOS-реализация |
|---|---|---|
| `tg_ws_proxy.py` | точка входа | `NEPacketTunnelProvider.startTunnel` + `packetFlow` цикл |
| `bridge.py` (`CryptoCtx`) | AES-CTR 4 контекста | `CryptoKit`/`CommonCrypto` |
| `bridge.py` (`MsgSplitter`) | разбор границ сообщений | свой класс на Swift/C |
| `pool.py` | пул WS | `URLSessionWebSocketTask` pool с прогревом |
| `balancer.py` | ротация доменов, cooldown | Actor с `Dictionary<String, Date>` |
| `raw_websocket.py` | WS-клиент | `URLSessionWebSocketTask` / `NWConnection` |
| `fake_tls.py` | маскировка TLS + active probing | `NWProtocolTLS` + свой парсер, **обязательно с реальным relay-backend**, не локальная имитация |
| `config.py`/`utils.py` | константы протокола | `enum`/`struct` |
| (нет аналога) | сборка IP-пакетов в TCP-поток | lwIP (C, BSD) + Swift-обёртка типа tun2socks-ios |

## 6. Язык реализации

- Основной язык — **Swift** (оркестрация, `NEPacketTunnelProvider`, конфигурация, lifecycle).
- **C** — для горячих участков (парсинг байт пакетов, крипто на высокой частоте), по аналогии с реальными проектами (TunnelKit: Swift 50.9% / C 32.9% / ObjC 15.9%; PIA tunnel-apple: Swift 72.7% / ObjC 26.5%).
- Кроссплатформенные фреймворки (Flutter/React Native/Xamarin) неприменимы — `.appex`-таргет требует чистого нативного кода.
- Entitlement `com.apple.developer.networking.networkextension` (Packet Tunnel provider type) — self-serve с 2016 года, специального разрешения Apple не требует.

## 7. Ограничения iOS 26/27 (актуально на сентябрь 2026)

- iOS 26 (осень 2025) добавил новый тип URL Filter в NetworkExtension — не критично для проекта, но показывает активное развитие фреймворка.
- iOS 27 вышел 14 сентября 2026 — публичных breaking-изменений в NetworkExtension не зафиксировано.
- Зафиксированы отдельные баги на iOS 26.4+ (например, подмена User-Agent в WKWebView внутри процесса расширения) — требует отдельного тестирования.
- **Лимит бесплатного Apple ID**: 3 сайдлоад-приложения одновременно, профили истекают через 7 дней. Платный Developer Program ($99/год) снимает оба ограничения — рекомендуется для стабильной долгосрочной схемы.
- Packet tunnel provider работает в user space — неизбежный performance overhead по сравнению с kernel-level VPN (признаётся самой Apple), но для трафика Telegram (текст + периодические медиа) не критично.
- Лимит памяти расширения (~15 МБ) — учитывать при выборе зависимостей, избегать раздутых Swift-библиотек.

## 8. Энергопотребление

- Постоянно активный туннель — примерно +5–15% CPU/батареи (аналогия с Shadowrocket и похожими VPN-прокси на Network Extension).
- Основная причина расхода — не обработка пакетов, а удержание радиомодуля активным (keep-alive пакеты через WS не дают Wi-Fi/сотовому модулю уходить в сон).
- Голосовые/видеозвонки в Telegram через туннель — заметно более высокий расход батареи (непрерывный поток пакетов).
- Митигация: `includedRoutes` только по IP Telegram (не глобальный VPN-режим), авто-disconnect тоннеля в простое/на сне устройства, отключение любого логирования в проде.

## 9. Дорожная карта реализации

1. **Прототип протокола** — консольный Swift-таргет без Network Extension, повторяющий логику `tg_ws_proxy.py` (парсинг хендшейка, DC-детект, AES-CTR), сверка байт с эталонным Python-выводом.
2. **Пустой Packet Tunnel Provider** — минимальный `NEPacketTunnelProvider` с `includedRoutes` только на IP Telegram, без обработки (просто пропуск пакетов) — проверка, что SwiftGram действительно начинает маршрутизироваться через процесс расширения.
3. **Интеграция lwIP/tun2socks** — реконструкция TCP-потока из сырых пакетов внутри `handlePacket`.
4. **Интеграция протокольного слоя** — встраивание логики шага 1 после lwIP-слоя, WS-транспорт вместо прямого TCP.
5. **Каскад фолбэков** — пул, ротация CF-доменов, cooldown/blacklist по образцу `balancer.py`. **Обязательно с реальным domain fronting / TCP-сплайсингом на существующий CF-backend**, а не локальной имитацией TLS — иначе повторится быстрый бан, зафиксированный при тестировании голого FakeTLS.
6. **Fake TLS слой** (опционально, если нужна доп. маскировка) — с ротацией среди набора реалистичных ClientHello-профилей (актуальные версии Safari/CFNetwork), не случайная генерация байт.
7. **Оптимизация батареи** — авто-disconnect на простое/сне, минимизация логирования, замена горячих участков на C.
8. **Инфраструктура** — платный Apple Developer аккаунт (снимает лимит 3 приложений и 7-дневное истечение профиля).
9. (Опционально) **Per-App VPN через `NETestAppMapping`** — если нужен точный контроль по списку конкретных Telegram-клиентов без захвата остального устройства.

## 10. Ключевые риски, которые нужно держать в голове при реализации

- Первый уровень фолбэка (прямой WSS к `web.telegram.org`) может не работать из-за L4-блокировки инфраструктуры Telegram — не тратить время на дебаг "почему не коннектится", это ожидаемо, сразу переходить к CF-уровням.
- Голый FakeTLS без реального backend'а для active probing — гарантированно быстро детектируется. Любая реализация маскировки обязана заканчиваться реальным сервером, отвечающим на зонды правдоподобно.
- Режим "белых списков" — форс-мажор, не лечится никакой технической маскировкой на клиенте; нужно закладывать в UX ("сервис временно недоступен из-за общего отключения") а не пытаться обойти программно.
- Ротация CF-доменов зависит от живого списка на GitHub — нужен собственный fallback/мониторинг, дефолтный список может выйти из строя в любой момент (лимиты Cloudflare на конкурентные WS-подключения).
- Мобильная сеть (4G/LTE) статистически чаще попадает под ограничения, чем домашний Wi-Fi — тестировать отдельно на обоих типах подключения.
